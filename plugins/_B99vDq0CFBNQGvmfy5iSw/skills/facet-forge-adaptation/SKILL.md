# 改编别人的技能（facet-forge-adaptation）

用户经常想拿现成的技能做底子。"参考"和"抄"之间有条线，这条线**由许可证划**，不由感觉划。

## 一、先分类：这个来源能不能用

| 来源 | 能不能改编 | 怎么处理 |
|---|---|---|
| 公开仓技能（GitHub 等） | **看 LICENSE**（见第二节） | 过门后按第三、四节改编 |
| 外部技能市场货架（壹座扩展市场里的外部条目） | ✅ 可参考 | 条目自带来源与审校标记；**仍要查原始许可** |
| 谦面其他创作者 pack 里的技能 | ⚠️ **默认不许** | 见第五节 |
| 用户自己写的/自己拥有的 | ✅ | 直接用 |

## 二、公开仓许可证门（硬门，不过就走人）

**查上游的 LICENSE 文件**。分三类：

| LICENSE | 判断 |
|---|---|
| MIT / Apache-2.0 / BSD / ISC | ✅ 可改编，**保留版权声明与许可证全文** |
| GPL / AGPL / LGPL | ⚠️ 可改编但有传染性——**先问平台运营**（我们的产物是商业供给面） |
| **CC BY-NC-ND** | ❌ **不可**（禁演绎 + 非商业，两条都踩） |
| **无 LICENSE 文件** | ❌ **不可**（默认保留全部权利） |
| 自定义/看不懂 | ❌ 不可，**除非用户能证明他有权** |

**没有 LICENSE 不等于可以白用**。这种时候正确的做法是：

1. 如实告诉用户："这个仓库没有许可证，法律上默认不可改编。"
2. 给出两条路：联系原作者求授权 / 我们从头写一份方法论（可以借鉴思路，不复制文本）。
3. **不要**"改几个字"就当自己的——这是最常见的越线方式。

## 三、改编的核心动作

改编不是抄一遍改措辞。**保留方法论，替换数据环节**：

| 上游技能里 | 改成 |
|---|---|
| 调某 API / 某 SDK 的代码 | 换成本平台在册 MCP 工具的调用（用发现工具查） |
| `pip install` / `npm i` 的依赖 | 去掉——技能里不能带执行依赖 |
| 上游自己的数据源 | 平台在册 server 的对应数据面 |
| 硬编码的路径/凭据 | 全部删掉（技能正文里**绝不能**出现真实凭据、IP、内网地址） |

**为什么这是核心价值**：上游技能的价值是"怎么做这件事"的方法论；数据从哪来是平台的事。
把方法论接上平台的真数据，才是可用的 pack；直接照搬会得到一个跑不起来的空壳。

## 四、改编稿必须带的三样

每一份改编稿都要有（这不是形式，是护栏）：

**1. attribution 块**（写在技能开头）：

```markdown
> 改编自 <来源仓 URL> 的 <技能名>（许可证：<LICENSE>，版权归原作者）。
> 本稿保留了原方法论，数据获取环节改为本平台 MCP 工具。
```

**2. 降级路径**——数据取不到时怎么办：

```markdown
数据未连接或取不到时，如实说明"这项数据当前取不到"，**不得**凭记忆或推测给出数字。
```

**3. 防编造硬约束**（按领域写具体）：

```markdown
所有数字必须来自工具实取并标注来源；未取到的项写「待核」，不得估算。
引用条款/案例必须实取原文，不得凭印象引用。
```

## 五、谦面其他创作者的 pack：默认不许抄

`facet_market_pack_read` 能看到别人 pack 里技能的全文——**看到不等于可以复制**。
manifest 目前没有许可证字段，别人没给许可，默认就是不许。

**可以做的**：学它的**结构**（怎么分技能、怎么组织提示、怎么接工具）。
**不可以做的**：复制它的文本内容。

用户说"参考 XX 套件"时：看结构、聊思路，文本自己写。**或者更简单——直接联系那位创作者**
拿许可（谦面详情页有作者信息）。

## 六、做完之后

改编稿和原创稿走**同一道门**：组装（`facet-forge-assembly`）→ 预校验 →
发布前复述 + 用户确认 → 发布 → 自查（`facet-forge-acceptance`）。

额外检查一项：**技能正文里不得残留上游的内网信息**。改完 grep 一遍
（IP、域名、令牌前缀、上游账号名）。
